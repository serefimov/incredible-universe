# Версии и публикация игры

## Проверять игру с телефона

После каждого push в любую рабочую ветку workflow «Публикация dev и release»
выполняет `npm run check`, собирает игру и публикует её без тега.
Откройте https://serefimov.github.io/incredible-universe/dev/ и выберите
последнюю сборку нужной ветки либо конкретный коммит в общем списке.
Адрес `dev/0.3.0-alpha.1-<12 символов SHA>/` постоянен: новая сборка
не заменяет старую. В списке видны исходная ветка, время сборки и коммит.
Если коммит опубликован из нескольких веток, содержимое сборки общее,
а последние ссылки этих веток указывают на один адрес.

Корень сайта предлагает dev и release. Стабильные выпуски находятся в
`release/X.Y.Z/`; старые ссылки `/X.Y.Z/` продолжают открывать их.
`versions.html` ведёт к обоим спискам. Dev не означает готовность MVP.

## VERSION и выпуск

При разработке VERSION содержит следующую релизную версию с суффиксом:
`0.3.0-alpha.1`. Допустимы alpha, beta, pre, rc и необязательный номер:
например `0.3.0-pre`, `0.3.0-rc.1`. Номер не обязан меняться при каждом push:
адрес различается хэшем. Changelog для разработки — раздел `## Не выпущено`.

Для стабильного выпуска:

1. В ветке задачи обновите VERSION до `X.Y.Z`, перенесите выпускаемые
   изменения под `## X.Y.Z` в CHANGELOG.md.
2. Дождитесь зелёного CI и слейте PR в main.
3. Создайте тег `vX.Y.Z` на этом коммите main. С телефона это можно сделать
   через Releases → Draft a new release → новый тег, Target: main → Publish release.
4. Дождитесь успешного workflow публикации и проверьте `release/X.Y.Z/`.
5. Продолжайте разработку с будущим номером и суффиксом в VERSION.

Push релизного коммита также создаёт dev: для стабильного VERSION адрес
получает суффикс `-pre` перед хэшем. Это не публикует новый release.
Стабильные теги обязаны совпадать с VERSION и соответствовать разделу
changelog; коммит выпуска должен находиться в истории main. Prerelease-теги
не используются для release. Не перемещайте опубликованные теги. Для повторной публикации используйте
новый workflow из рабочей ветки: повторный запуск старого workflow из тегов
v0.1.0/v0.2.0 использует прежние правила сайта. Архив от этого не удаляется,
но dev снова появится на сайте только после новой публикации из ветки.

## Однократная настройка GitHub

- Settings → Pages → Source: GitHub Actions.
- Settings → Environments → github-pages → Deployment branches and tags:
  **No restriction**, чтобы разрешить публикацию из всех веток и тегов.
  Прежнее разрешение только для тегов v* блокирует автоматический dev-деплой.
- Actions должны быть разрешены; бот workflow должен иметь возможность
  создавать и обновлять служебную ветку `pages-archive`. Если используются
  rulesets, разрешите это действие для этой ветки. Workflow запрашивает
  contents: write только у job архивирования.

Личный токен в Secrets не нужен: используются GITHUB_TOKEN и OIDC Pages.
Разрешение веток окружения владелец задаёт в GitHub; код workflow его не меняет.
Публикация из веток относится к веткам этого репозитория. Push в чужой fork
не публикуется на сайте исходного репозитория.

## Архив и параллельная публикация

Pages заменяет весь сайт. Поэтому готовые HTML, лицензии, changelog и
метаданные хранятся в служебной ветке `pages-archive`. Она исключена из
триггера push. Не удаляйте и не редактируйте её вручную: это архив сайта.
Исторические выпуски импортируются из стабильных тегов.

Каждая сборка сохраняется до входа в очередь Pages. Запись использует
обычный push без force; при конкурирующем обновлении архив перечитывается
и объединяется заново. Старые адреса проверяются на совпадение исходного
коммита и содержимого, повторная сборка не переписывает их. Ссылки последних
сборок веток упорядочиваются по GitHub run ID, чтобы позднее завершение
старого workflow не откатывало ссылку ветки.

Только job деплоя сериализован. GitHub может объединять ожидающие деплои,
но сборки уже находятся в архиве. Job читает текущий полный архив внутри
очереди и публикует все dev и release. Ошибочный build/check не архивируется.

Автоматической очистки пока нет: архив растёт. При приближении к ограничениям
GitHub Pages потребуется отдельная задача с правилами хранения.

## Проверки

```sh
npm ci
npm run check
```

Проверки включают сохранение двух сборок с одним VERSION, старых выпусков,
неизменность адресов, валидацию версий и повторную/конкурентную запись архива
в локальный bare-репозиторий. Исходный Spike остаётся байт в байт.
