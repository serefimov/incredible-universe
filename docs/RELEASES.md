Публикация подготовлена в рамках #1. Первый номер продукта — `0.1.0`;
это выпуск исторического прототипа, а не готового MVP. Тег `v0.1.0` опубликован 2026-10-02. Модульная основа с фиксированным шагом и двумя временами подготовлена к выпуску
`0.2.0`. Публикация произойдёт после слияния PR #21 и создания тега `v0.2.0`
на коммите `main` с `VERSION = 0.2.0` и разделом `## 0.2.0` в changelog.

## Что настроить владельцу один раз

1. В Settings → General → Default branch выбрать `main`. Для этого
   репозитория настройка уже выполнена.
2. В Settings → Pages → Build and deployment выбрать Source: **GitHub Actions**.
   Не добавлять предложенный шаблон: workflow уже есть в репозитории.
3. В Settings → Environments → `github-pages` разрешить развёртывание тегов
   `v*` (Selected branches and tags → Add deployment branch or tag rule → Tag).
   Если окружение ещё не создано, создать его. Правило только для основной
   ветки блокирует workflow, запущенный тегом.
4. Убедиться, что Actions разрешены и разрешены официальные `actions/*`.
   Если используются настройки по умолчанию публичного репозитория, отдельной
   настройки обычно не требуется.

Для деплоя не нужны личный токен или SSH-ключ в Secrets: GitHub предоставляет
`GITHUB_TOKEN` и OIDC. Разрешения публикации выдаются только job `deploy`.
Workflow не меняет настройки Pages автоматически.

Официальная документация: [workflow Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages),
[источник публикации](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site),
[окружения](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments).

## Подготовить выпуск

1. В ветке соответствующей задачи обновить `VERSION` в формате `X.Y.Z` и
   добавить раздел `## X.Y.Z` в `CHANGELOG.md`. Коммит — в прошедшем времени,
   например `#1 подготовил выпуск 0.1.0`.
2. Проверить выпуск и влить PR в `main`. Публикация проверяет, что все теги
   выпуска указывают на коммиты из истории `main`.
3. На нужном коммите `main` создать и отправить аннотированный тег:

   ```sh
   git switch main
   git pull --ff-only
   git tag -a v0.2.0 -m 'Выпуск 0.2.0'
   git push origin v0.2.0
   ```

4. Дождаться успешного workflow «Публикация версий игры» во вкладке Actions.
   Если настройки Pages ещё не готовы, настроить их и выбрать Re-run jobs.
   Проверить корень сайта и адрес с версией на смартфоне.

Только отправка тега `vX.Y.Z` запускает публикацию. Push в ветку и обычный PR
запускают проверки. Предварительные версии вроде `v0.2.0-rc.1` пока не
поддерживаются: такой запуск завершается ошибкой без публикации.

Каждый запуск собирает **все** теги выпуска и целиком публикует их каталоги:
новая версия не стирает предыдущие. HTML берётся из соответствующего тега,
а не из текущей рабочей копии. Повторная публикация старого тега не откатывает
корень сайта. Не перемещать и не удалять опубликованные теги: они служат
архивом версий; их удаление удалит каталог при следующей публикации.
Для исправления выпускать новую версию. Для большого архива нужно будет
учесть ограничения размера GitHub Pages.

## Проверить локально

Нужен Node.js 20 или новее. Зависимость сборки закреплена в package-lock.json:

```sh
npm ci
npm run check
node tools/build-pages.mjs
```

Последняя команда требует хотя бы одного локального тега выпуска и создаёт
`dist/pages/`. Каталог игнорируется Git. Не создавать выпускной тег в рабочей
ветке только ради проверки: тесты используют временные репозитории.

`release.json` указывает HTML и, для новой основы, входной JS-модуль и CSS.
Сборка в `tools/build-game.mjs` превращает их в самостоятельный HTML. Публикация
использует содержимое каждого тега, включая все относительные JS-импорты и CSS,
а не текущую рабочую копию. Старые теги без поля `bundle` копируются байт в байт.

Выпуск `0.1.0` по-прежнему содержит `prototypes/spike_0_3.html`. Новая точка
входа — корневой `index.html` и модули `src/`. esbuild установлен через `npm ci`
и в локальной проверке, и в workflow будущих выпусков. Опубликованная игра
не обращается к npm или внешним JS/CSS-файлам. `VERSION` — единственный источник
номера продукта; обновлять его и changelog нужно до нового тега.

При добавлении внешних ресурсов или другого сборщика адаптировать упаковку
до выпуска. Старые модульные версии собираются закреплённым сборщиком workflow,
который запускается; если его когда-либо заменить, проверить совместимость
архива. Физический результат проверяется отдельно от байтов сборки.

## GitHub без браузера

Предпочтительный путь для issues и PR — API или GitHub CLI. При инициализации
подключение GitHub возвращало `403 Resource not accessible by integration`
на операции записи; поэтому использовался вход владельца в браузере.
Доступ по SSH для Git не даёт доступа к REST API.

После установки и входа GitHub CLI работает; используйте его для записи.
Для нового окружения установить `gh` из [официального источника](https://cli.github.com/),
войти через `gh auth login --hostname github.com --git-protocol ssh --web`
и проверить `gh auth status`. Вход выполняет владелец; секреты не нужно
отправлять в чат. После входа issues и PR можно создавать командами
`gh issue create` и `gh pr create`, а milestone и прочие операции — `gh api`.
Примеры и параметры: [GitHub CLI](https://cli.github.com/manual/).
