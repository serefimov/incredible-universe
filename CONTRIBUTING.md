# Как работать над The Incredible Universe

## Задача, ветка и коммиты

1. Выберите GitHub issue и проверьте её цель, зависимости и критерии приёмки.
2. Создайте отдельную ветку для этой задачи. Имя начинается с номера issue: `1-init`, `2-game-foundation` и т. п. Одна задача — одна ветка.
3. Делайте атомарные коммиты: один самостоятельный результат в одном коммите. Не объединяйте несвязанные изменения.
4. Каждое сообщение коммита начинается со ссылки на задачу: `#1 добавил README и настройки репозитория`. Описывайте выполненное действие в прошедшем времени, со строчной буквы после номера задачи; не пишите «Добавить», «Исправить» и другие инфинитивы.
5. Перед передачей на review выполните проверки по задаче и опишите результат, отклонения и ограничения проверки. Не закрывайте задачу, если обязательный критерий ещё не выполнен.

Секреты, локальные настройки, результаты сборки и временные материалы проверки не коммитятся.

## Перед изменениями игры

Прочитайте [AGENTS.md](AGENTS.md), [GAME_DESIGN.md](docs/GAME_DESIGN.md), [PHYSICS.md](docs/PHYSICS.md) и [DECISIONS.md](docs/DECISIONS.md). Явные новые указания владельца имеют приоритет над документами.

Исходный `prototypes/spike_0_3.html` сохраняется байт в байт. Изменения игры делайте в новой реализации; прототип нужен для сравнения. Не исправляйте найденные в нём дефекты в ходе аудита.

Факты текущего кода и требования к будущей игре описывайте отдельно. Формулы, константы, новые механики и правила из открытых вопросов становятся принятыми только после соответствующего решения. Обновляйте связанные документы при изменении утверждённого поведения.

## Проверки

Для воспроизведения аудита исходного скрипта нужен Node.js 20 или новее:

```sh
node tools/audit-spike.mjs
```

Это проверка реального скрипта с имитацией DOM и входных событий; она не заменяет браузер и физический смартфон. Визуальные проверки и их ограничения записываются в [SPIKE_AUDIT.md](docs/SPIKE_AUDIT.md).

После изменения игровой механики проверяйте полный цикл: расстановка → Play → наблюдение → Reset → правка → повторный запуск. Обязательные крайние случаи: столкновение, сброс после полёта, перенос и удаление тела. Проверяйте мышь и касания; результат при одинаковых начальных условиях должен воспроизводиться.

Не вводите стек или зависимости только ради оформления репозитория. Добавляйте инструменты по потребности конкретной задачи и документируйте выбор.

## Версии и GitHub

Порядок публикации, версия, changelog и работа через API/CLI описаны в
[RELEASES.md](docs/RELEASES.md). Обновляйте `VERSION` и `CHANGELOG.md` перед
выпуском в ветке соответствующей задачи. Опубликованные теги не переписываются.

Перед review изменений публикации выполняйте:

```sh
node tools/build-pages.mjs --check
node --test tools/build-pages.test.mjs
```
